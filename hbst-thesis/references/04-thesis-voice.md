# 论文语气与措辞（Thesis Voice）

> 阶段二动笔前必读。核心：**论文正文读起来要像学生论文，而不是助手工作日志、源码审计报告或交付说明。** 证据/过程性内容只允许存在于 `paper-context/` 内部工作区文件，正文直接陈述系统本身。

## 1. 可用句式（中性学术口吻）

- `本文设计并实现了……`
- `本系统采用……`
- `该模块主要完成……`
- `为了保证……，系统……`
- `系统通过……实现……`
- `测试结果表明……`
- `综上所述……`

## 2. 禁止进入正文的措辞（一旦出现即返工）

过程/证据泄漏类：
- `根据现有代码……` / `根据项目源码……`
- `从代码证据看……` / `根据 README 和 PRD……`
- `当前材料只提供……` / `当前可读取项目……`
- `本文不编造……` / `待补真实程序截图` / `占位图` / `（待补充）`
- 本地文件路径（如 `D:\...`）
- 源码文件名（`init.sql`、`pom.xml`、`application.yml`）出现在普通正文叙述里（作为"系统配置文件包含……"的泛指可，点名文件路径不可）

## 3. 改写对照（Bad → Good）

| Bad（禁止） | Good（可用） |
|---|---|
| 根据项目源码和 SQL 脚本可知，系统已完成主要后端接口。 | 系统已完成主要后端接口和数据库设计，能够为……提供基础业务支撑。 |
| 当前材料未提供前端截图，因此第五章保留截图占位。 | 本文按登录、首页、××、××四个场景安排运行效果图，展示主要功能在页面端的实际效果。 |
| 从代码证据看，多个接口进行了角色判断。 | 权限控制不能只依赖前端隐藏按钮，还需要在后端接口中读取当前用户角色并进行判断。 |
| 该接口在 service 层做了事务（源码见 OrderServiceImpl）。 | 订单创建涉及库存扣减、订单保存与日志写入，系统在服务层通过事务保证这些操作同步完成。 |

## 4. 与降 AIGC 规范的衔接

- 语气规范解决"不像工作日志"；humanize 规范解决"不像 AI"。两者同时生效：先按本节保证内容直接陈述，再按 humanize A/B/C 做节奏与结构的人化处理。
- humanize 的"具名引用（A3）"在此落为：综述里把"有研究指出"改成"××（年份）在……中提出/发现"；**没有真实文献依据时标【待作者补充】，不得编造学者与文献**。
- 全文"基础嗓音"：本科论文档 = 陈述为主、适度使用"为保证/通过……实现"式因果句、极少第一人称"我"（致谢除外）、不用网络语。

## 5. 交付前自查

- [ ] 正文无任何"证据/源码/待补/占位/当前材料/不编造"措辞
- [ ] 正文无本地路径与源码文件名点名
- [ ] 图片缺失时正文以"本文安排……效果图"式陈述，而不是"此处缺图"
- [ ] 随机抽读任意两段，风格一致（无"一段重写一段原样"断层，humanize C1）
